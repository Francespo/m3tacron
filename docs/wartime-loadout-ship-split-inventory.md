## 1. Summary

XWA split the Resistance **BTA-NR2 Y-Wing** into two chassis:

- `btanr2ywing` — the original Y-Wing; its pilots have the **Intuitive Interface** ship ability and `Wartime Loadout` remains a separate configuration upgrade.
- `btanr2wywing` — a second Y-Wing entry; its pilots have the upgrade's effect baked in as the **Devastating Barrage** ship ability, plus 2 extra shields and a white Reload action.

The XWA source shipped the split as **pilot variants with a `-wartime` suffix pointing at a second ship xws**. m3tacron stores and resolves XWS ids in several places, but the split is not handled consistently anywhere: historical and new XWS forms of the same real-world squadron produce different identities, the new chassis has no pilot→ship mapping, and the new ship xws has no icon glyph. This report inventories the impact and lists candidate fixes without implementing them.

## 4. The pre-split entry and the two new variants

### 4.1 Pre-split (Legacy and pre-split XWA)

- Ship `btanr2ywing` = `BTA-NR2 Y-Wing`, Small, attack 2 / agility 1 / hull 4 / **shields 3**, actions Focus, red Lock, red Barrel Roll, red Boost. (`external_data/xwing-data2-legacy/data/pilots/resistance/bta-nr2-y-wing.json`, and the same file in XWA.)
- Upgrade `wartimeloadout` = `Wartime Loadout`, type Configuration, granted effect "Gain 1 Torpedo slot and 1 Missile slot. Replace your ship ability with the following (Devastating Barrage)." Legacy cost **5**; XWA cost **0**.
- Pilots used the base xws (e.g. `zoriibliss`) and the upgrade was listed under `configuration`.

### 4.2 Post-split (current XWA)

Source files (XWA submodule):

- `external_data/xwing-data2/data/pilots/resistance/bta-nr2-y-wing.json` → `xws: btanr2ywing`
- `external_data/xwing-data2/data/pilots/resistance/bta-nr2-w-y-wing.json` → `xws: btanr2wywing`

The second file (note the doubled `w` in the filename and xws) is the integrated-loadout variant:

| | `btanr2ywing` (no loadout) | `btanr2wywing` (integrated) |
|---|---|---|
| Name | BTA-NR2 Y-Wing | BTA-NR2 Y-Wing |
| Shields | 3 | **5** |
| Actions | Focus, red Lock, red Barrel Roll, red Boost | Focus, **white Lock**, red Barrel Roll, red Boost, **white Reload** |
| Pilot ship ability | Intuitive Interface | **Devastating Barrage** |
| Pilot xws | `zoriibliss`, `tezanasz`, … | `zoriibliss-wartime`, `tezanasz-wartime`, … |
| Points (XWA, examples) | Zorii 11, Teza 8, Wilsa 8, Shasa 9, Lega 8, Aftab 7, Corus 9, C'ai 7, New Republic Patrol 7, Kijimi Spice Runner 9 | Zorii 12, Teza 11, Wilsa 11, Shasa 11, Lega 10, Aftab 10, Corus 11, C'ai 10, New Republic Patrol 10, Kijimi Spice Runner 11 |

The `-wartime` pilot variants (10 of them) all carry `ship: btanr2wywing`. They exist **only in XWA**; the Legacy dataset has neither `btanr2wywing` nor any `-wartime` pilot.

`Wartime Loadout` still exists as an upgrade in XWA (`cost 0`, `standard: true`), still restricted to `ships: ["btanr2ywing"]` and marked `standardized: true`. So both paths to the integrated loadout are still present in the data: the old `btanr2ywing` + `wartimeloadout` upgrade, and the new `btanr2wywing` + `-wartime` pilot.

**Leftover / duplicated rows:** there are no duplicate *ship* rows for one xws, and no duplicate `wartimeloadout` upgrade rows, but two distinct ship entries now share the display name "BTA-NR2 Y-Wing" with different xws (`btanr2ywing`, `btanr2wywing`), and the upgrade that used to represent the variant is still present. That is the source of the "duplicated/confused historical data".

## 5. Other XWA splits of the same class

Searching the XWA submodule for upgrade-turned-into-ship patterns (ship-name duplicates and pilot-id suffixes):

- **Only `BTA-NR2 Y-Wing` has one chassis name mapped to two different ship xws values in the same faction** (`bta-nr2-y-wing.json` → `btanr2ywing`, `bta-nr2-w-y-wing.json` → `btanr2wywing`). All other duplicated ship names are the *same* xws shared across factions (e.g. `fangfighter` Rebel/Scum, `tielnfighter` Rebel/Empire).
- The `-wartime` pilot suffix is unique. Other pilot-id suffixes are pack/box variants (`-battleofyavin`, `-battleoverendor`, `-evacuationofdqar`, `-siegeofcoruscant`, `-armedanddangerous`, `-epicsl`, `-legendsandrelics`, `-ssl`), store/limited variants (`-lsl`), pilot-specific chassis reprints (`caithrenalli-btanr2ywing`, `wedgeantilles-rz1awing`), or cross-faction reprints (`-rebelalliance`, `-scumandvillainy`). None of those bake an upgrade into a new chassis.
- `external_data/xwing-data2/data/quick-builds/resistance.json` references the Y-Wing family; no other chassis shows the "upgrade → dedicated variant" shape.

**Conclusion:** as of this data revision the Y-Wing is the only same-class XWA split, so a targeted fix is sufficient and generalising is not yet justified. This should be re-checked at each XWA points update, since the same treatment could be applied to other `standardized` configurations.

## 6. XWS import/export paths and why codes break

### 6.1 Where XWS is read (import) and written (export)

- **Import from builders:** `backend/scrapers/web_utils.py` `fetch_xws_from_builder` / `_extract_yasb_xws` drives the YASB UI (`button.view-as-text` → `button.select-xws-view` → textarea) and `json.loads` the exported XWS. Scrapers store it verbatim in `list.list_json` (`backend/scrapers/*.py`).
- **Canonical identity (used as the squad "code"):** `backend/utils/list_keys.py` `get_list_key` builds `canonical_signature` from pilot ids + upgrade xws; `get_ship_list` builds `ship_list` from the `ship` fields. `backend/scripts/scrape_tournaments.py` and `migrate_normalize_list.py` persist both.
- **Backend hydration:** `backend/utils/xwing_data/parser.py` `parse_xws` resolves pilot ids and upgrade xws to names.
- **Frontend resolution/export:** `frontend/src/lib/stores/xwingData.svelte.ts` `getPilot`/`getShip`/`getUpgrade` (with pack-suffix stripping); `backend/utils/yasb.py` `xws_to_yasb_url` / `get_xws_string` exist for YASB links/JSON export (not wired to any frontend button found in this repo).
- There is **no user-facing "paste an XWS code" endpoint**: all routers expose GET endpoints only (plus the Ko-fi webhook), so "XWS codes" on the site means the ids inside scraped/stored squads and the `canonical_signature`/`ship_list` derived from them, not a paste-to-import feature.

### 6.2 Reproduced breakages

**(a) Same squadron, two different identities (historical duplication).**
Running the real `get_list_key` / `get_ship_list` on the two XWS forms of the same list:

```
HIST canonical_signature: [{"upgrades": [{"xws": "wartimeloadout"}], "xws": "zoriibliss"}]
NEW  canonical_signature: [{"upgrades": [], "xws": "zoriibliss-wartime"}]
HIST ship_list: btanr2ywing
NEW  ship_list: btanr2wywing
```

The pre-split and post-split encodings of the same real-world squad are counted as two different lists and two different chassis.

**(b) The new chassis has no analytics mapping (data loss).**
`pilot_ship_mapping` (live dev DB) contains **0 rows** for the wartime pilots:

```
         pilot          | list_entries | mapped_rows
------------------------+--------------+-------------
 zoriibliss-wartime     |           71 |           0
 wilsateshlo-wartime    |            6 |           0
 tezanasz-wartime       |            5 |           0
 newrepublicpatrol-wartime |         3 |           0
```

`backend/analytics/ships.py` inner-joins `pilot_ship_mapping psm ON psm.pilot_xws = (p->>'id') AND psm.source = :source`, so every stored squadron that uses a `-wartime` pilot is **dropped from ship analytics** — even though `list.ship_list` contains `btanr2wywing`. The ship page therefore shows stats for old `btanr2ywing` squads but silently omits the new ones.

**(c) The new ship xws has no icon (red "?" in the UI).**
`frontend/src/lib/components/StatIcon.svelte` maps ship xws → glyph chars; it contains `btanr2ywing: "{"` but **no `btanr2wywing`**. `StatIcon` lowercases/strips the type, fails the map lookup, then falls back to the raw string; because its length is > 1 it sets `isError` and renders a red `?`. The XWA font CSS likewise defines `.xwing-miniatures-ship-btanr2ywing` only (`external_data/xwing-miniatures-font/dist/xwing-miniatures.css:1139`).

Confirmed against live production (`m3tacron.com`, read-only, 2026-09-18):

- CSS rule count on the loaded page: `.xwing-miniatures-ship-btanr2ywing` = **1**, `.xwing-miniatures-ship-btanr2wywing` = **0**.
- `GET /ship/btanr2ywing`: header glyph `::before { content: "{" }`, rendered box 14.8 x 24 px.
- `GET /ship/btanr2wywing`: same header glyph `::before { content: none }`, rendered box **0 x 0 px** — the icon is blank, while the page still lists the 10 `-wartime` pilots (`/pilot/zoriibliss-wartime`, …). The ship-detail template also uses `StatIcon type={data.shipXws} isShip` (`frontend/src/routes/ship/[xws]/+page.svelte:633`), which would render the red `?` wherever that block is populated.

**(d) Cross-source resolution fails silently.**
`get_pilot_info("zoriibliss-wartime", DataSource.LEGACY)` → `None`; `get_ship_info("btanr2wywing", DataSource.LEGACY)` → `None`. XWA-created ids cannot resolve when the site is toggled to Legacy, and neither could a future Legacy squad id resolve in XWA.

**(e) Historical payload still resolves to the old semantics.**
`parse_xws` on the historical form returns ship "BTA-NR2 Y-Wing" **and** a `Wartime Loadout` configuration upgrade, while the new form returns the same ship name with no upgrade. The displayed effect is duplicated/ambiguous, matching the user's report.

## 8. Impact assessment

1. **Historical duplication:** the same real squad is counted twice (old + new XWS), and historical rows still show the now-integrated upgrade as a separate card.
2. **Silent analytics loss:** 76 stored squads (85 wartime pilot entries) never reach the ship analytics because `pilot_ship_mapping` has no `-wartime` rows. This is the most damaging, because nothing errors — the numbers are just wrong.
3. **Missing ship icon:** both Y-Wing chassis share the display name, but only `btanr2ywing` has a glyph; `btanr2wywing` renders a blank header icon (confirmed live) and a red `?` wherever the `StatIcon` fallback path is used.
4. **Two ship pages for one chassis:** `/ship/btanr2ywing` and `/ship/btanr2wywing` split popularity/stats that users read as one ship; the shipped `frontend/static/data-xwa/xwing-data.json` also contains both.
5. **Cross-source source toggle:** XWA `-wartime` ids return `None` under Legacy, so those entries render as raw ids.

## 9. Candidate minimal fixes (NOT implemented)

Ranked by value / risk. Any chosen option still needs the user's decision; the confirmed product authority is official XWA ids and points for the two variants, the old ship id must remain a deprecated alias, and historical migration must be contextual (a squad that also held the `Wartime Loadout` upgrade becomes the integrated variant, otherwise the plain variant).

1. **Add an alias/fallback layer for the wartime ids (lowest risk, no data rewrite).**
   - Files: `backend/utils/xwing_data/pilots.py` (`get_pilot_info`), `ships.py` (`get_ship_info`), `upgrades.py` (`get_upgrade_info` if needed), `frontend/src/lib/stores/xwingData.svelte.ts` (`getPilot`/`getShip`).
   - Treat `zoriibliss-wartime` as the wartime variant and resolve `-wartime` ids; expose `btanr2ywing` as a deprecated alias that can point at either variant depending on context. Removes the `None` results and raw-id display.
   - Trade-off: does not by itself fix analytics or historical counting; needs a canonical direction so counts do not double.

2. **Refresh `pilot_ship_mapping` and make it resilient (high value, low risk).**
   - Files: `backend/scripts/populate_pilot_ship_mapping.py` (re-run), or add the missing rows. Both wartime pilots (`btanr2wywing`) and the base mapping must be present.
   - Trade-off: one-off data operation; must be scheduled after every XWA data bump, otherwise the drift recurs. Could be paired with a startup/deploy check.

3. **Contextual historical migration of `list_json` / `canonical_signature` / `ship_list` (matches the product decision; medium risk).**
   - Files: a new migration under `backend/scripts/` (pattern: `migrate_*.py`) plus `backend/utils/list_keys.py` if the canonical form should prefer the wartime id.
   - For rows containing a `-wartime`-less pilot **and** `wartimeloadout`, rewrite the pilot to the integrated variant and drop the upgrade; otherwise leave as the plain variant. Preserve the old id as an alias so old links keep resolving.
   - Trade-off: irreversible in place without a backup; changes stored historical data; must be idempotent and reversible.

4. **Add the missing icon glyph (trivial, cosmetic).**
   - Files: `frontend/src/lib/components/StatIcon.svelte` (map `btanr2wywing` to the same glyph as `btanr2ywing`), and/or regenerate/alias the font CSS.
   - Trade-off: cosmetic only; does not fix data.

5. **Generalise split handling (defer).**
   - Files: `backend/utils/xwing_data/*`, scrapers, frontend store; a suffix/alias registry for upgrade-turned-ship splits.
   - Trade-off: unjustified today because the Y-Wing is the only same-class split in the current XWA revision; adds abstraction without a second case.

Recommended order if the user approves a fix: (2) mapping repair + (1) alias layer first (restores correctness with no data rewrite), then (3) historical migration, then (4) icon. (5) only when a second same-class split appears.
