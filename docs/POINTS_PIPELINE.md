# Points & game-data pipeline

How a points release travels from the upstream data repos to production, and
what to do when a step fails.

## Chain

```
SogeMoge/xwing-data2-legacy   (Legacy points + changelog reports)
Francespo/xwing-data2         (XWA data; YASB feed is still manual)
        │  git submodules
        ▼
Francespo/xwing-unified-data  ── 05:00 UTC daily
  scripts/sync_data.py --sync-submodules --detect-points
  • updates the nested submodules
  • Legacy: reads changelog/*.md (any name) and records date/version/counts
  • XWA: only 50P version commits; ignores versions already recorded
  • writes points_history/*.json and pushes main
        │  external_data submodule
        ▼
Francespo/m3tacron            ── 06:00 UTC daily
  scripts/sync_game_data.py --sync-submodules --rebuild-manifests
  • advances external_data to unified main (nested pins stay upstream-owned)
  • regenerates data-xwa/data-legacy manifests + points-history.json
  • scripts/validate_points_pipeline.py
  • opens/updates the chore/game-data-sync PR
  • enables auto-merge (no bot account required)
        │  merge → Coolify auto-deploy
        ▼
production                    api.m3tacron.com / m3tacron.com
        │
        ▼
Pipeline Health (4×/day) + external uptime monitor
```

## Required settings

### GitHub App (`SYNC_APP_ID` / `SYNC_APP_PRIVATE_KEY`)

A **private** GitHub App installed only on `Francespo/m3tacron`:

- Repository permissions:
  - **Contents: read/write** (checkout and branch push)
  - **Pull requests: read/write** (create/merge)
  - **Metadata: read-only**
- Webhook off, OAuth off, “Only on this account”.
- Add the App ID and private key as repository secrets
  **`SYNC_APP_ID`** and **`SYNC_APP_PRIVATE_KEY`**.

The workflow mints a one-hour installation token with
`actions/create-github-app-token@v2` and uses it for checkout, push, PR
creation and merge. The PR is authored by the app, so the `pull_request` CI
runs; with **Required approvals = 0** auto-merge merges it after the checks.

Why not `GITHUB_TOKEN`: events generated by `GITHUB_TOKEN` do **not** trigger
`pull_request` workflows, so a `GITHUB_TOKEN`-created PR never gets its checks
and auto-merge waits forever. The “Allow GitHub Actions to create and approve
pull requests” setting alone does not solve that.

The app does not sign commits. If `Require signed commits` is enabled in
`Protect main`, the PR stays `BLOCKED` unless the workflow is configured with a
GPG signing key; the recommended setup is to leave that rule off for this
repository.

### Review policy on `Francespo/m3tacron`

Repo → **Settings → Rules → Rulesets → Protect main**.

- **Recommended (solo maintainer):** set **Required approvals = 0**. CI is
  still required; the workflow creates the PR and auto-merge merges it when
  green. No bot/approver account is needed.
- **If you want a review:** keep approvals ≥ 1 and use a different approver
  (a GitHub App or another account). Auto-merge will wait for that review; the
  health workflow flags a PR stuck for more than 24 hours.
- `Francespo/xwing-unified-data` and `Francespo/xwing-data2` have no PR/review
  rules; their workflows push directly.
- The old `SYNC_BOT_TOKEN` / `Franc3s-bot` approval path has been removed.

## Validation

Run locally:

```bash
python3 scripts/validate_points_pipeline.py
pytest backend/tests/test_points_history.py -q
```

The validator checks ISO dates, newest-first ordering, `latest_date` matching
the first update, no duplicates/future dates, frontend vs `external_data`
agreement, and non-empty generated manifests. It runs in PR CI and in the sync
workflow before the PR is opened.

## Failure modes

| Symptom | Check | Fix |
|---|---|---|
| Unified workflow red | Actions → `Sync Game Data & Auto-detect Points` | Rerun; inspect the submodule/changelog error |
| Points released but not detected (Legacy) | `SogeMoge/xwing-data2-legacy/changelog/` contains a report with `**Date**` and `**Total Cards Updated**` | Ask upstream for the report, or add the entry manually |
| Points released but not detected (XWA) | `Francespo/xwing-data2` → `Sync YASB points` run | Check the YASB version commit / diff guard; rerun with `version`/`date` overrides |
| Sync PR open > 24h | `chore/game-data-sync` PR | Check `SYNC_APP_*`, CI checks and `Protect main` approvals |
| Deploy drift | `Pipeline health` issue / `Deploy Drift Check` | Redeploy the `main` app in Coolify |
| API unreachable | `Pipeline health` issue | `docker ps`, backend logs, Coolify deployment |
| Deployed points stale | API `date_range` vs repo `points-history.json` | Merge the sync PR, wait for deploy |
| Wrong date/version recorded | `points_history/*.json` | Revert the unified data commit; fix the source report |

`Pipeline Health` runs at 01:15, 07:15, 13:15 and 19:15 UTC. It maintains a
single issue `Pipeline health: points/data drift` and closes it automatically
when the checks pass. It complements, but does not replace, the external uptime
monitor (the monitor detects “the site is down”; the health workflow detects
“the site is up but the data is stale”).

## Manual release

1. Add or fix the changelog report in the source repo.
2. Run `xwing-unified-data` → `Sync Game Data & Auto-detect Points`.
3. Run `m3tacron` → `Sync Game Data` (or wait for 06:00 UTC).
4. Let auto-merge merge the `chore/game-data-sync` PR (or approve it if
   `Protect main` still requires a review).
5. Confirm `/api/meta-snapshot?...&time_range=points_update` shows the new date.

## XWA / YASB feed

Implemented in `Francespo/xwing-data2` by `.github/workflows/sync-yasb-points.yml`
(04:30 UTC, before unified):

1. finds the latest YASB commit whose subject is a points version (`2.1.1`);
2. fetches `cards-common.coffee` at that commit and at its parent;
3. diffs only `points`/`loadout` and applies the release diff to
   `data/pilots` and `data/upgrades`;
4. commits `data: apply YASB 50P x.y points (YYYY-MM-DD)` and pushes `master`;
5. unified 05:00 parses the version/date, updates the submodule and points_history;
6. m3tacron 06:00 opens the data PR and auto-merges it.

The data repo is not a full YASB mirror; only the release diff is applied, and a
diff over 100 entries is refused. A YASB release without a version-shaped commit
subject needs a manual `workflow_dispatch` with `version`/`date` overrides.

The first run applies the missing 2.1.1 items (Boba Fett variants and the
Marauder title).
